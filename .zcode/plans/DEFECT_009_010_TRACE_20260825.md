## Why a single fix closes both defects

Both scenarios share **the same mechanical gap**: the elseif branch at line 3010 excludes the case where `total_penalty == 0` but `refund_amount > 0`. The H1 walk-back at line 3174 (which posts the inverse of `refundTreasuryAccount`) is **nested inside** that elseif block — so when penalty is zero, H1 is structurally unreachable even though its **own** guard (`refund_amount > 0.001`) would be satisfied.

| Aspect | DEFECT-009 | DEFECT-010 |
|---|---|---|
| Number of payments | 1 | 3 |
| refund_amount | 8000 | 30000 |
| Code path diverging from fix-target | **Identical** | **Identical** |
| `reverseSinglePayment` loop iterations | 1 (all skipped) | 3 (all skipped) |
| Step 3 elseif block | FALSE | FALSE |
| H1 walk-back | SKIPPED (same reason) | SKIPPED (same reason) |
| H2 sweep | SKIPPED (same reason) | SKIPPED (same reason) |
| Step 4 carrier credit-back | early-return (0) | early-return (0) |
| **Mechanism** | **Same — only the refund_amount magnitude differs** |

A single change to the elseif condition — extending it to also fire when `refund_amount > 0.001` — closes both defects with one line of code.

## Why this fix does NOT affect the DEFECT-005/006 fix

The DEFECT-005/006 fix added **H1** (refund walk-back at line 3174) and **H2** (residual sweep at line 3084) inside the existing elseif block. The proposed fix changes only the **condition** of that elseif, not the bodies of H1/H2.

| Trigger | Current behaviour | After proposed fix | Impact on 005/006 |
|---|---|---|---|
| `existingRefund == null` | elseif FALSE → nothing | elseif FALSE → nothing | **No change** |
| `existingRefund != null`, `penalty == 0`, `refund == 0` | elseif FALSE → nothing | elseif FALSE → nothing | **No change** (full-penalty cancel without refund) |
| `existingRefund != null`, `penalty == 0`, `refund > 0` | elseif FALSE → **DEFECT-009/010** | elseif TRUE → H2 guard skips (pending=0), H1 fires (refund>0.001) | **Fixed** |
| `existingRefund != null`, `penalty > 0`, `refund == 0` | elseif TRUE → H2 fires (sweep), H1 guard skips (refund==0) | elseif TRUE → same | **No change** (005/006 scenario 3) |
| `existingRefund != null`, `penalty > 0`, `refund > 0` | elseif TRUE → H2 fires (sweep), H1 fires (walk-back) | elseif TRUE → same | **No change** (005/006 scenario 2) |
| Cross-currency KWD/EUR (refund > 0) | elseif TRUE (penalty usually > 0 too) → H1 throws `BusinessLogicException` | elseif TRUE → H1 still throws | **No change** |

The DEFECT-005/006 regression tests (`CashboxReversalAfterCancelTest`) cover rows 5 and 6 of the table above. They will continue to pass because their trigger conditions (`penalty > 0`) are unchanged.

## What the fix code WILL look like (preview only — NOT applied in Step 1)

> ⚠️ **Preview only. Do not apply yet.** The user has requested a stop after Step 1 (trace) for review and approval.

```php
// CURRENT (line 3010):
} elseif ($existingRefundEarly && ((float) $existingRefundEarly->airline_penalty + (float) $existingRefundEarly->office_penalty) > 0.001) {

// PROPOSED (line 3010):
} elseif ($existingRefundEarly && (
    ((float) $existingRefundEarly->airline_penalty + (float) $existingRefundEarly->office_penalty) > 0.001
    || ((float) $existingRefundEarly->refund_amount) > 0.001
)) {
```

Why this is the minimum-invasive change:
- Adds one boolean clause (`|| refund_amount > 0.001`).
- No change to H1 / H2 bodies — both keep their internal guards.
- H2's internal guard (`pending_sales_receivable.balance < -0.001` at line 3085) auto-skips the no-op transfer when pending is already at 0 (the typical zero-penalty cancel state).
- H1's internal guard (`refund_amount > 0.001` at line 3174) auto-skips when refund is zero.
- Cross-currency guard at line 3180 unchanged.

Step 2 (test confirmation) and Step 3 (formal before/after code) follow in the next phase upon user approval.

## Customer_AR side-effect — confirmed closable as a side benefit

Both Scenario A (P+F, refund=8000) and Scenario B (I+F, refund=30000) leave customer_AR at a non-zero balance after cancel:

| Scenario | customer_AR after cancel | customer_AR after delete (current code, no fix) | After H1 fires (with fix) |
|---|---|---|---|
| A (P+F, refund=8000) | +8000 | +8000 ❌ | 0 ✓ |
| B (I+F, refund=30000) | +30000 | +30000 ❌ | 0 ✓ |

The same H1 transfer that restores cashbox (`customer_AR → cashbox refund_amount`) simultaneously zeroes out customer_AR. This is **the same root cause as DEFECT-007** (cancel-side over-statement of customer_AR), but for the `penalty=0` sub-case. The proposed fix closes both the cashbox leg AND the customer_AR leg of this scenario.

To document the side-effect formally (not just as a code comment), an explicit `$this->assertEqualsWithDelta(0, $customerAR->balance, 0.01, '...')` line is added to both regression tests, firing independently from the existing `assertAllBackToBaseline` foreach. The DEFECT-007 backlog remains open for the `penalty > 0` cases (out of scope for this PR).
