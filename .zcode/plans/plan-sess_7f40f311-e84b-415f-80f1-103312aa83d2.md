# Plan: Dry-run Script for Duplicate Income Transactions + Fix Script

## Context (root cause — confirmed from code)

`BusBookingService::payBooking()` records the payment as `type='income'` (BUG). The correct type is `type='transfer'`. This causes:

- 47 active bookings → 2 income transactions each (sale + payment) → 94 income tx where there should be 47
- Income sum doubled: 46,630 EGP instead of 23,115 EGP
- P&L sees revenue=0 because filters by `related_type='bus_bookings'` but data uses `App\Models\Bus\BusBooking`
- Variance -9,635 EGP (and tx#303, ghost balances separate)

User chose scope = **comprehensive** + fix approach = **dry-run shows both scenarios, choose later**.

---

## Goal

Build **one** read-only dry-run script that:
1. Enumerates every duplicate pair (sale + payment)
2. For each pair, classifies the original (lower tx_id) and the duplicate (higher tx_id)
3. Examines account_entries for both
4. Simulates **two fix scenarios** and shows the projected impact:

| Scenario | Action | DB change | Account balance change | New tx count |
|---|---|---|---|---|
| **A: Re-type only** | UPDATE `type` from `income` → `transfer` on duplicate | 1 UPDATE per duplicate | none (entries unchanged) | unchanged |
| **B: Reverse + re-create** | Insert additive reversal tx + new transfer tx | 2 INSERTs per duplicate | restores from double-count | +94 |

5. Shows the **projected trial balance** for each scenario (income, expense, current_capital, expected_capital, variance)
6. Lists **residual issues** that prevent variance from reaching 0 (ghost balances, tx#303, P&L bug)
7. Outputs a structured report

After dry-run review, the fix script will be created.

---

## File to create

### `scripts/dryrun_dup_bus_income.php` — read-only dry-run (~520 lines)

#### Structure
- **[1] Environment + safety guards** — APP_ENV, DB, source-scan for any `INSERT|UPDATE|DELETE|TRUNCATE|DROP` keywords (defensive check)
- **[2] Identify duplicate groups** — `GROUP BY related_type, related_id, amount HAVING COUNT(*) > 1`, lowest id = original
- **[3] Per-pair detail (pre-reversal)** — tx details, account_entries, account balance BEFORE
- **[4] Scenario A simulation** — re-type only, no balance change
- **[5] Scenario B simulation** — reverse + re-create, in-memory only
- **[6] Aggregated impact** — comparison table
- **[7] Residual issues** — tx#303, 25 ghost balances, P&L revenueRows
- **[8] Recommendations** — which scenario to apply
- **[9] Save JSON** to `storage/logs/dryrun_dup_bus_income_<timestamp>.json`

## Safety guarantees

- **Zero writes** — confirmed by the source-scan guard
- **No service-layer calls** — raw DB::select only
- **Pre/post counters snapshot** for integrity verification
- **Wrapped-in-tx simulation** — Scenario B is in-memory, no DB::beginTransaction
