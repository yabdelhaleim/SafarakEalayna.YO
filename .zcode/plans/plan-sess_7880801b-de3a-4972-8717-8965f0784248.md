## Retest Structure (PHPUnit class — 50–65 tests)

Organised in `@group` blocks matching the user's 17 phases:

### §A — Baseline / Setup (5 tests)
- `test_baseline_ledger_starts_balanced` — fresh DB, all clearing accounts exist, FX rates seeded, EGP/USD/SAR/KWD wallets present.
- `test_baseline_office_cashbox_is_default_bus_vault` — `Account::getModuleVault('bus')` returns office EGP cashbox.
- `test_baseline_per_currency_ar_accounts_are_independent` — same customer, EGP+USD AR, both exist.
- `test_baseline_clearing_accounts_resolve_for_each_module` — income + expense for bus.
- `test_baseline_currency_service_resolves_four_currencies` — USD/SAR/KWD/EUR → EGP via direct + inverse + through-EGP.

### §B — Booking Creation (6 tests)
- EGP Mode A + Mode B with `ledger_globally_balanced`.
- Foreign-currency Mode A (USD) — assert customer AR in USD, supplier AP in EGP, both legs posted.
- Foreign-currency Mode B (SAR) auto-inventory — assert `exchange_rate_to_egp` snapshot on booking.
- Multi-quantity foreign-currency (KWD × 3) — assert conversion precision to 6 dp.
- Validation: zero qty, negative qty, qty > available, selling < cost (all rejected with no ledger movement).

### §C — Payment Flows (8 tests)
- Full EGP, full USD, full SAR via HTTP.
- Partial EGP then top-up to paid.
- Multi-payment aggregation (3 partials = 1 full).
- Payment with `Idempotency-Key` (replay = no-op, same row).
- Payment with safety-net 5s tuple window (Carbon warp).
- Overpayment rejected (no ledger movement).
- Payment on cancelled booking rejected (no ledger movement).
- Payment with currency-mismatched treasury rejected (HTTP 422, no rows).

### §D — Cancellation Deep Audit (8 tests)
- Unpaid cancel — Δ=0 on cashbox, customer AR unchanged, status=Cancelled.
- Paid cancel, no penalty — full refund, status=Refunded, cashbox Δ=−paid, customer AR cleared.
- Paid cancel, 100% penalty — refund=0, status=PartiallyRefunded, cashbox Δ=0, supplier AP cleared.
- Paid cancel, partial penalty — refund=paid−penalty, status=Refunded.
- Cancel USD booking paid from USD wallet — refund in USD, no FX loss.
- Cancel USD booking paid from EGP cashbox — refund in EGP via FX, no balance drift.
- Double-cancel — second throws Arabic `الحجز ملغي أو مسترد بالفعل`.
- Cancel after `pay-debt` — **blocked** (conservation guard pinned from `BusBookingFlowTest:356`).

### §E — Simple `deleteBooking` (3 tests)
- Unpaid delete — inventory restored, supplier cleared, customer AR cleared, ledger balanced.
- Paid delete — throws Arabic `لوجود مدفوعات` (no deletion, no reversal).
- Already-cancelled delete — just hides row, no double reversal.

### §F — `deleteBookingWithReversal` (5 tests)
- Partial-paid delete — Δ=0 on cashbox + customer AR + supplier AP + inventory.
- Fully-paid delete — Δ=0 across all layers.
- Multi-payment delete — 3 payments reversed, soft-deleted, Δ=0.
- Double-delete — throws `هذا الحجز محذوف بالفعل`.
- `BusRefundRequest.transaction_id` nulled (Fix #12) — assertion added.

### §G — Inventory Debt Lifecycle (4 tests)
- Deferred inventory partial debt → full debt pay — supplier AP 0, cashbox −debt.
- Cash inventory delete reverses expense — cashbox back to baseline.
- Deferred inventory delete with paid debt — soft-deleted, `remaining_debt` preserved on row.
- Inventory delete with bookings — rejected.

### §H — Cross-Currency HTTP Layer (6 tests — **fills the largest gap**)
- USD booking → USD wallet pay (no FX on the GL).
- USD booking → EGP cashbox pay (FX on payment).
- SAR booking → SAR wallet pay (no FX).
- SAR booking → EGP cashbox pay (FX).
- KWD booking via HTTP → EGP cashbox pay (high-rate precision).
- Customer AR with EGP + USD + SAR balances simultaneously (stacking).

### §I — Idempotency / Duplicate Movement (5 tests — **fills the gap**)
- Triple payment replay with same `Idempotency-Key` — 1 row, 3 responses identical.
- Same-key replay after first call returned 422 — no row created on retry.
- Same-key replay with different `payment_method` — rejected.
- Same-key replay with different `amount` — rejected.
- Same-key replay across different bookings — independent (no cross-booking lock).

### §J — Concurrency (4 tests — **fills the gap**)
- 2 simultaneous payments on same booking with same key — DB-level lock guarantees 1 row.
- Pay vs cancel on same booking at same time — final state consistent.
- 2 simultaneous `deleteBookingWithReversal` — second throws.
- 2 simultaneous `cancelBooking` — second throws (status already Cancelled).

### §K — Mutation Lock (4 tests — **fills the gap**)
- After payment, direct `$booking->update(['total_price' => 0])` is silently ignored OR blocked.
- After payment, `$booking->update(['currency' => 'EUR'])` blocked by Guard.
- After delete, direct `$booking->restore()` does not bring back payments.
- After cancel, `$booking->update(['status' => 'Pending'])` blocked.

### §L — Illegal / Invalid States (5 tests — **fills the gap**)
- Refund unpaid booking — throws.
- Refund > paid amount — throws.
- Refund twice — second rejected.
- Pay amount=0 — rejected.
- Pay amount negative — rejected.
- Cancel after already-Refunded — rejected.

### §M — Database-Level Audit (4 tests — **fills the gap**)
- After full lifecycle, exactly N transactions exist (1 sale, 1 cost, payments, reversals).
- After delete, soft-deleted rows visible via `withTrashed` but absent from default queries.
- No orphan `AccountEntry` rows (every entry linked to an active transaction).
- No transactions with `related_id` pointing to soft-deleted bookings (after `deleteBookingWithReversal`).
- Income tx uniqueness — second `recordIncome` for same booking throws (`BusBookingPaymentTypeTest`).

### §N — Reconciliation / Conservation (3 tests)
- Opening + inflows − outflows = closing (cashbox, customer AR, supplier AP).
- Booking financial state = sum of related transactions.
- Refund: original − refund = 0 net on customer AR.

**Total target: ~62 new tests.** Test methods numbered `test_retest_<section>_<n>` to align with HajjUmra precedent.

## Test Methodology (per scenario)

1. **Snapshot** pre-operation balances (cashbox, bank, customer AR, supplier AP, income clearing, expense clearing, vault).
2. **Execute** via service layer (preferred) AND HTTP endpoint (for `§H`/`§J`).
3. **Assert** transaction row count, type, amount, currency, debit/credit legs, `related_type/id`.
4. **Reconcile** Δ on each affected account against expected.
5. **Idempotency** — replay once, twice, three times; assert no drift.
6. **DB-direct** final inspection — `BusBooking::withTrashed()`, `Transaction`, `AccountEntry`, soft-delete columns.

## Risks

- **SQLite vs MySQL** — `BusTestCase` uses SQLite. The `refunded` enum extension and the income-tx unique-key migration self-skip on SQLite. Will document this limitation in the report.
- **Concurrency tests on SQLite** — limited true parallelism; will use `DB::beginTransaction` + sequential simulation + claim conservative coverage.
- **Time** — 62 tests × setup × FX lookups ≈ several minutes. Will run with `--stop-on-failure` first, then full re-run.
