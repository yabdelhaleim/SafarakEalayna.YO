# Plan: Comprehensive E2E Audit Script for the Flight Module

## Goal
Deliver **one** in-process PHP script — `scripts/flight_module_e2e_audit.php` — that simulates every real user operation in the flight module on **Local/Staging only**, commits each scenario to the DB so the data can be browsed mid-run, and then automatically deletes everything it created while guaranteeing zero impact on pre-existing data.

---

## 1. Hard safety guards (block before anything else)

The script refuses to run unless all of these pass:

1. **`APP_ENV` is not `production`** — read from `config('app.env')`. If it is, abort with a clear Arabic error and exit code 2.
2. **DB is not the production connection** — compare `config('database.connections.mysql.database')` (or sqlite path) against a small deny-list of keywords (`prod`, `production`, `live`); abort if matched.
3. **Interactive confirmation** — print a one-line summary of what is about to be written and require the operator to type `YES` to proceed (skip with `--yes` / `-y`).
4. **Pre-snapshot** — before any write, the script counts rows in 19 critical tables and stores the counts in `storage/logs/flight_audit_snapshot_<timestamp>.json`. Every `DELETE` later is filtered by the audit prefix `FM-AUDIT-` and the post-cleanup counts must match the pre-snapshot exactly. If they don't, the script aborts cleanup, prints a diff, and exits 3.

If the operator passes `--read-only` the script still runs every scenario but wraps the entire execution in `DB::beginTransaction` … `DB::rollBack`.

---

## 2. Audit prefix scheme

Every created row carries a unique tag in a string column + a sentinel in `notes` / `description`, tied together by a single **run UUID** so cleanup is one `WHERE notes LIKE '%<run-uuid>%'` per table and cross-table checks can join on it.

| Table | Tag location |
|---|---|
| `customers.full_name` | prefix `FM-AUDIT-CUST-…` |
| `flight_bookings.booking_reference` / `notes` | prefix `FM-AUDIT-FLT-…` + uuid in notes |
| `flight_carriers.name` | prefix `FM-AUDIT-CARRIER-…` |
| `flight_systems.name` | prefix `FM-AUDIT-SYSTEM-…` |
| `flight_groups.name` | prefix `FM-AUDIT-GROUP-…` |
| `airline_accounts.name` | prefix `FM-AUDIT-AIRL-AC-…` |
| `treasuries.name` | prefix `FM-AUDIT-TRS-…` |
| `accounts.name` | prefix `FM-AUDIT-ACC-…` |
| `transactions.notes` | contains `FM-AUDIT-<uuid>` |
| `flight_payments.transaction_reference` | prefix `FM-AUDIT-PAY-…` |
| `flight_refunds.notes` | contains `FM-AUDIT-<uuid>` |
| `refund_requests.notes` | contains `FM-AUDIT-<uuid>` |
| `ticket_modifications.notes` | contains `FM-AUDIT-<uuid>` |
| `currencies.code` / `airports` | unchanged (reuse existing USD/EGP, CAI/JED) |

## 3. Master data setup (idempotent `firstOrCreate`)

- currencies: EGP (rate 1.0), USD, SAR, KWD (reused, not created)
- airports: CAI, JED, RUH (looked up)
- flight_carrier (FM-AUDIT-CARRIER-EGP) — EGP, credit_limit 1,000,000
- flight_system (FM-AUDIT-SYSTEM-EGP) — EGP, credit_limit 1,000,000
- flight_group (FM-AUDIT-GROUP-EGP) — EGP, credit_limit 1,000,000
- airline_accounts (FM-AUDIT-AIRL-AC-EGP / -USD) — matching currency
- treasuries (FM-AUDIT-TRS-EGP-CASHBOX / -USD-CASHBOX / -EGP-BANK)
- accounts (FM-AUDIT-ACC-EGP-CASHBOX / -USD-CASHBOX / -EGP-BANK / customer AR)
- customers (FM-AUDIT-CUST-… × 4 — 2 EGP, 2 USD)

Carriers/systems are recharged 500,000 EGP / 50,000 USD at startup so purchases never hit `InsufficientBalanceException`.

| # | Scenario | Currency | Expected end state |
|---|---|---|---|

| S02 | Book EGP, partial then full payment | EGP | CONFIRMED, paid |
| S03 | Book EGP, overpayment attempt (must reject) | EGP | ValidationException |
| S04 | Book USD, payment in same USD cashbox | USD | CONFIRMED, paid |
| S05 | Book USD, payment in EGP cashbox (cross-currency) | USD | CONFIRMED, paid |
| S06 | Book USD, partial then full payment | USD | CONFIRMED, paid |
| S07 | Book + cancel with full refund (zero penalties) | EGP | REFUNDED, balances restored |
| S08 | Book + cancel with penalty (partial refund) | EGP | PARTIALLY_REFUNDED |
| S09 | Book + cancel with no refund (penalty == sale) | EGP | CANCELLED |
| S10 | Book USD + cancel with full refund | USD | REFUNDED |
| S11 | Book USD + cancel with penalty | USD | PARTIALLY_REFUNDED |
| S12 | RefundRequest → process (airline_credit) | EGP | voucher active, carrier debited |
| S13 | RefundRequest → process (agency_treasury) | EGP | treasury credited, GL posted |
| S14 | Reverse a processed RefundRequest | EGP | refund request soft-deleted |
| S15 | Modification create + confirm (airline_change_fee) | EGP | confirmed_at set, ledger posted |
| S16 | Reverse a confirmed Modification | EGP | ledger reversed, booking fields restored |
| S17 | Delete-with-reversal (never cancelled) | EGP | booking soft-deleted, ledger reversed |
| S18 | Delete-with-reversal (after cancel) | EGP | residual cleared, booking soft-deleted |
| S19 | Idempotency: double delete (must throw) | EGP | RuntimeException on 2nd |
| S20 | Group booking + pay-debt (cross-currency) | EGP | debt recorded then cleared |
| S21 | Carrier recharge from EGP bank, book via carrier | EGP | CONFIRMED |
| S22 | System recharge from EGP bank, book via system | EGP | CONFIRMED |
| S23 | Customer debt pay (TX-201 regression) | EGP | customer balance 0 |
| S24 | Final invariant sweep across all created rows | — | all checks pass |

Each scenario is wrapped in `safeRun($id, $name, fn() => runScenario($n))` that catches `Throwable`, records the error + trace, and continues.

## 5. Per-scenario invariant checks (PHP Eloquent)

After every scenario the script runs scenario-specific assertions, e.g.:

- **After S01 (Book + full payment)**: `selling_price = sum(payments.amount)`, `sale_gl_transaction_id` set and points to a balanced transaction (`Σdebit = Σcredit` within 0.011), customer AR balance = -sellingPrice, carrier balance = opening - purchaseEGPInCarrierCurrency, prepaid flight_carrier GL = opening - purchaseEGP.
- **After S07 (Cancel full refund)**: `flight_tickets.status='cancelled'`, carrier balance restored to opening, customer AR = 0, cash box = opening - sellingPrice, `flight_refunds.status='processed'`, `sale_gl_transaction_id` is NULL, 3 new `account_entries` rows (sale reversal + cash refund).
- **After S12 (RefundRequest airline_credit)**: `airline_credits.status='active'` with expiry set, `airline_transactions` row (type='debit'), carrier debited, no GL row, booking status = PARTIALLY_REFUNDED, cumulative-refund cap holds.
- **After S14 (Reverse refund)**: RefundRequest soft-deleted, AirlineCredit soft-deleted (`status='cancelled'`), carrier balance restored, booking status unchanged (documented GAP).
- **After S15 (Modification confirm)**: `TicketModification.status='confirmed', confirmed_at NOT NULL`, `flight_bookings.last_modified_at` updated, `modification_count++`, airline account debited, prepaid flight_carrier GL debited, 3 account_entries (cash debit, payable credit, revenue credit).
- **S24 final sweep** runs all 21 SQL invariant queries from the audit report.

## 6. Output

- **Console**: color-coded pass/fail per scenario + final summary table (`scenario_id | check | expected | actual | suggestion`).
- **JSON**: `storage/logs/flight_module_audit_<timestamp>.json` with `run_uuid`, `started_at`, `finished_at`, `app_env`, `db_connection`, `db_database`, `pre_snapshot`, `post_snapshot`, per-scenario `assertions`, aggregate `issues`, summary `{total, passed, failed, skipped}`.

---

## 7. Cleanup (after all scenarios)

1. For each table, run `DELETE WHERE notes LIKE '%<run-uuid>%'` (or prefix match). Order respects FK constraints (children first).
2. For immutable `account_entries` / `transactions`: leave entries (project convention is additive reversal); the script's docblock explains the trade-off and `--no-cleanup` for manual inspection.
3. Re-count critical tables → compare to `pre_snapshot`. If mismatch, write a diff report and exit 3.
4. Delete the snapshot file only after post-snapshot equals pre-snapshot.

## 9. CLI

```
php scripts/flight_module_e2e_audit.php                  # interactive, commit + cleanup
php scripts/flight_module_e2e_audit.php --yes             # skip confirm
php scripts/flight_module_e2e_audit.php --read-only       # wrap in transaction, always rollback
php scripts/flight_module_e2e_audit.php --no-cleanup      # keep data after run
php scripts/flight_module_e2e_audit.php --only S01,S02,S07
php scripts/flight_module_e2e_audit.php --skip S12,S13
```

## 11. Out of scope (explicitly)

- Filament pages (UI, not booking logic).
- Aviation API path (`AviationService::createBooking`) — divergent flow; script prints a one-line note pointing to it.
- Queued listener lag — real risk but not reproducible from a script.
- HTTP API coverage — script uses services directly, mirroring the existing `flight_module_full_e2e.php` pattern.
