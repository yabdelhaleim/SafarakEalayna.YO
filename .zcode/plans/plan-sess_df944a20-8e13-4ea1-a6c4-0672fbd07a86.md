## خطة اختبار الداش بورد الرئيسية الشامل (Admin Main Dashboard)

### 📋 الهدف
اختبار شامل لـ `GET /api/v1/dashboard` والتحقق من أن **كل كرت** يعرض نتيجة صحيحة ويحسبها بشكل سليم، مع تقرير بأي bugs يتم اكتشافها (بدون إصلاح).

### 🎯 النطاق
- **Endpoint**: `GET /api/v1/dashboard` (admin auth)
- **Cards**: 24+ كرت موزعين على 3 tabs (tourism, office, treasury)
- **Trial balance endpoints**: `/api/v1/reports/trial-balance`, `/office-trial-balance`, `/consolidated-trial-balance`
- **البيئة**: Local مع SQLite (الـ `phpunit.xml` يستخدم `:memory:` SQLite)
- **التعامل مع bugs**: تقرير فقط (بدون إصلاح)
- **GUI**: manual عبر `browser-use:web-gui-tester` skill

### � نمط الـ Inline Fixtures

كل test يبني بياناته بنفسه باستخدام:
- `User::query()->create([..., 'role' => 'admin'])` — للأدمن
- `Employee::query()->create(['user_id' => ..., 'status' => 'active'])`
- `Account::query()->create([...])` (مع `LedgerBalanceMutationGuard::run(...)` لو الـ balance > 0)
- `Customer::factory()->create()`
- `FlightBooking::query()->create([...])` / `BusBooking::factory()->create()` / إلخ
- للحسابات المالية، استخدام `LedgerClearingAccounts` و `ReportFinanceService` بنفس النمط في `DashboardFinancialStatsTest.php`

**Cache bypass**: كل request يستخدم `?nocache=1` لأن `CACHE_STORE=array` لا يدعم tags.

### ⚠️ معوقات معروفة متوقعة

1. **بعض الـ factories مش موجودة** (`FlightBooking`, `VisaBooking`, `HajjUmraBooking`, `OnlineTransaction`, `WalletTransaction`, `Employee`, `Invoice`, `FlightCarrier`, `FlightSystem`) → نستخدم raw `Model::query()->create(...)`.
2. **`AccountObserver` بيكتب opening balance تلقائياً** لو الـ balance > 0 → لازم نستخدم `LedgerBalanceMutationGuard::run(...)` لتجنب double-posting.
3. **Profit بييجي من الـ GL مش من الـ booking column** → عشان نختبر `data.tourism_summary.flights.profit` محتاجين نعمل transfer rows في الـ GL (نمط `DashboardFinanceInclusionTest.php`).
4. **Data قد تكون ناقصة في بعض الـ modules** → الـ tests هتتعامل مع `null` و `0` بشكل صحيح.
5. **الـ Dusk/Chromedriver** قد يحتاج setup إضافي لو مش شغال من قبل.
