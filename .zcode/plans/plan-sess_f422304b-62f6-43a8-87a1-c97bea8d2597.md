# خطة إصلاح وفحص موديول الطيران (Flight Module Audit + Fix)

## التشخيص

بعد قراءة الـ source code بدقة، تم تأكيد **3 bugs حقيقية** في `app/Services/Flight/FlightBookingService.php` تفسّر كل شكاوى المستخدم:

| # | Bug | الموقع | التأثير |
|---|-----|--------|---------|
| **FIN-A** | `deleteBookingWithReversal` يستخدم `ensureFlightIncomeClearingAccount()` بدل `pendingSalesReceivableIdForFlight()` في فرع الـ residual reversal | السطور 2790-2861 | يولّد **revenue وهمي** على income clearing، يفسد الأرباح و salbe الـ P&L |
| **FIN-B** | `cancelBooking` لا يُنشئ income-reversal لاسترداد الإيراد المُعترف به في `addPayment` (قيد `type=Income`) | السطور 2271-2327 | بعد الإلغاء `totalRevenues` في P&L يبقى كما هو بدل أن يُصفر |
| **FIN-C** | إذا `refundCashboxId == 0` في فرع `elseif`، الكود يكتفى بـ `Log::warning` ويترك الـ residual معلّقاً | السطور 2814-2818 | الرصيد المعلق يبقى في `pending_sales_receivable` بدون تنظيف |

**السبب الجذري:** الـ commit `d0e73fd` (FIN-2, 2026-08-23) غيّر الحساب المستخدم في `recordSaleToCustomer` من `income_clearing.flight` إلى `pending_sales_receivable.flight`، لكن:
- فرع `elseif` في `deleteBookingWithReversal` لم يُحدّث ومازال يستخدم الحساب القديم
- `cancelBooking` لا يعكس قيد الإيراد الفعلي المُسجّل في `addPayment` (هذا قصور قديم لم يلتفت له FIX-2)

## المرحلة 1: الإصلاحات في `app/Services/Flight/FlightBookingService.php`

### Fix FIN-A (deleteBookingWithReversal elseif branch)
**السطور 2790-2861:** تغيير الحساب المستخدم من `ensureFlightIncomeClearingAccount` إلى `pendingSalesReceivableIdForFlight`.

```php
// قبل:
$clearingAccountId = $this->ensureFlightIncomeClearingAccount($userIdEffective);
// ...
'to_account_id' => $clearingAccountId,        // ❌ income clearing (خاطئ)

// بعد:
$placeholderAccountId = $this->ledgerClearingAccounts
    ->pendingSalesReceivableIdForFlight();
// ...
'to_account_id' => $placeholderAccountId,    // ✓ pending sales receivable (صحيح)
```

### Fix FIN-B (cancelBooking revenue reversal)
**السطور 2280-2328:** إضافة معالجة جديدة بعد Step 3 تبني revenue-reversal لكل قيد `type=Income` تم إنشاؤه في `addPayment`:
- الاستعلام: `Transaction` حيث `related_type=FlightPayment` و`related_id IN (flight_payments.id لهذا الحجز)`.
- لكل قيد، يُنشأ mirror transfer بنفس الـ from/to لكن يُغيّر `type` من `income` إلى `expense` (لتُسجَّل كـ `operating_expense` بدون تأثير على revenue_net).

**أو حل أنظف:** إضافة method جديد `reverseFlightBookingRevenue($booking)` في الـ service نفسه، يُستدعى في `cancelBooking` بعد الـ sale reversal.

### Fix FIN-C (orphan residual handling)
**السطور 2814-2818:** بدلاً من `Log::warning` فقط، اعمل posting منفصل `income_clearing.flight → pending_sales_receivable.flight` (internal transfer) ليُصفّر الـ residual. هذا يحدث تلقائياً دائماً ويغطّي الحالة الحرجة.
