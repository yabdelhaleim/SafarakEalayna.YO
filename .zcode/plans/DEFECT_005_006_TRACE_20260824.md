## Where the reversal is missing or wrong

### Two distinct accounting bugs both manifest as "cashbox loss during delete-after-cancel"

#### Bug A (scenario 3): FIN-A misroutes the residual clearing through the cashbox

**Premise of FIN-A** (line 3009-3138): "The cashbox received the kept penalty cash; on delete, debit it back out."

**Reality**: In scenario 3, the cancel's FIN-B already reversed the income (cashbox −12000, customer_AR +12000). The cashbox never received any "extra" cash from the kept penalty — the income was already walked back. The 12000 sits on:
- `customer_AR`: +12000 (over-stated by FIN-B reversal)
- `pending_sales_receivable`: -12000 (never cleared because Step 3 sale reversal posted 0)

**Correct destination for the residual**: should be cleared via FIN-E-style sweep — `customer_AR → pending_sales_receivable` 12000. This is exactly what FIN-E (line 3140-3190) does for the no-payment case. We need an analogous branch for the **paid-but-no-refund** case.

#### Bug B (scenario 2): The refund-legitimate 14000 cashbox debit is never walked back

In scenario 2, the customer got a 14000 cash refund during cancel (legitimate). The test expects `assertBalancesUnchanged(snapshot)` — i.e., after a delete-with-reversal the cashbox should return to its pre-booking state. This means **the 14000 refund debit must be walked back during delete**.

But the current code:
- Step 2 (loop payments) is **skipped** because `existingRefund.refund_amount > 0.001`
- Step 3 `if` branch is skipped because `existingRefundEarly` is set
- Step 3 `elseif` (FIN-A) only handles the **residual** (= penalty kept = 1000 in scenario 2). It doesn't touch the 14000 refund.
- No Step 4 (carrier credit-back) in this scenario (purchase_balance_source was carrier, but the airline_penalty covers the entire carrier cost)
- → **14000 is permanently lost from the cashbox**

The cancel-with-refund branch needs to: **credit the cashbox back by `refund_amount`** during delete. This is the inverse of `refundTreasuryAccount`.

- Current H1 design has no FX conversion logic → would **throw** → `DB::transaction` rolls back → soft-delete does NOT happen → caller sees error

### Decision (Option B): H1 throws `BusinessLogicException` for cross-currency

**Why throw, not skip silently**:
- The user explicitly wants this surfaced (not unknown behavior). An exception forces the operator to take action.
- `BusinessLogicException` is the project's canonical "state conflict" exception, already mapped to HTTP 409 in `bootstrap/app.php:90-95`.
- The exception is **not** input validation (which would be 422) — the inputs are valid; the server's state cannot safely reverse the cross-currency refund walk-back with the current code.

**Why 409, not 422**:
- `BusinessLogicException` is the established pattern for state-conflict errors (see `bootstrap/app.php:90-95` and `FINDING UX-1 REMEDIATION` comment).
- 422 (ValidationException) is reserved for input-shape errors.

**Required side-changes (to be applied in Step 4)**:
1. Fix `FlightController::destroy` (line 349-359): currently catches `\Exception` and returns 422 — must explicitly rethrow `BusinessLogicException` so the global handler maps it to 409. Same pattern we already applied to `addPayment` in DEFECT-001 fix.
2. Add `// KNOWN LIMITATION (2026-08-24)` comment near the throw.
3. Add a backlog entry for the KWD-refund walk-back design.

## DEFECT-007 — customer_AR over-stated after cancel (permanent, not transient)

**Discovered during**: Trace review for DEFECT-005/006 (2026-08-24, second pass)
**Severity**: HIGH — affects every cancelled booking currently in production
**Scope**: ALL cancellations with refund_amount > office_penalty (i.e., customer got cash back)

### Symptom

When a booking is cancelled with a refund, the customer's AR ledger ends up at a permanently-incorrect positive balance even though the customer actually paid us net-of-refund.

Example trace (scenario 2: book 25000, pay 15000, cancel with 1000 penalty, refund 14000):

| # | Action | customer_AR balance |
|---|---|---|
| 0 | Initial | 0 |
| 1 | createBooking sale 25000 | +25000 |
| 2-3 | 2 addPayments totaling 15000 | +10000 |
| 4 | cancel Step 3 (sale reversal 24000) | −14000 (transient) |
| 5-6 | FIN-B reverses addPayment income ×2 | +1000 |
| 7 | cancel refund 14000 (cashbox → customer_AR) | **+15000** (PERMANENT) |

**Expected after cancel**: customer_AR = +1000 (the office penalty kept — net economic position)
**Actual after cancel**: customer_AR = **+15000** (over-stated by 14000)

### Why this matters

The customer_AR balance represents the customer's net debt to us. After cancel-with-refund, the customer should owe us only the office_penalty kept as revenue (=1000). The +15000 in the ledger implies the customer still owes us 15000 — which is **factually wrong**:
- Customer already paid 15000 (cash in)
- Customer already got 14000 back (cash out)
- Net: customer paid 1000, the office kept it as revenue
- Ledger should show customer owes +1000, not +15000

If a finance/admin reports the customer_AR ledger, this number is materially misleading.

### Production impact

Every cancellation with a partial refund leaves customer_AR over-stated by `refund_amount`. Examples:
- 1 booking with refund 1000 → customer_AR over by 1000
- 100 bookings with avg refund 5000 → customer_AR over by 500000
- This accumulates across the entire cancellation history

**Status**: This is in production NOW. Every cancelled-not-deleted booking exhibits it.

### Root cause (inside `cancelBooking`)

Two distinct operations both post to customer_AR:
1. **Step 3 sale reversal** (line 2364): debits customer_AR by `saleReversalAmount` (= selling - penalty). Reduces the recorded sale.
2. **FIN-B revenue reversal** (line 2437): uses `reverseTransaction` which adds back the income entry (customer_AR +amount).
3. **refundTreasuryAccount** (line 2726): credits customer_AR by `refund_amount`.

These three operations don't net to zero when `refund_amount > office_penalty`. Specifically:
- Net effect on customer_AR = −saleReversalAmount + total_paid_income + refund_amount
- = −(selling − penalty) + total_paid + (total_paid − penalty)
- = 2 × total_paid − 2 × penalty + penalty − selling
- For scenario 2: 2×15000 − 2×1000 + 1000 − 25000 = 30000 − 2000 + 1000 − 25000 = +4000 ≠ 0

The math doesn't add up because the cancel logic wasn't designed to balance customer_AR — it was designed to balance the cashbox + carrier + revenue, with customer_AR as an implicit balancing account that absorbs the discrepancy.

### Affected flows

- Any `POST /flight/bookings/{id}/cancel` with `refund_amount > 0.001`
- All EGP, USD, KWD, EUR, SAR, GBP booking currencies (customer_AR is always EGP)
- Direct cancellations via `FlightBookingService::cancelBooking()` and any code path that calls it (UI button, API, batch jobs)

### What is NOT affected

- The DEFECT-005/006 fix (this PR's H1 + H2) walks customer_AR back to **0** during delete — over-correction fully resolved
- The 5 baseline scenarios (1, 4, 5, 6, 7) — they don't go through cancel-with-refund
- Bookings cancelled with `refund_amount == 0` (full penalty kept) — already correctly balanced by FIN-B

### Proposed fix (out-of-scope for DEFECT-005/006 PR)

After the cancel transaction, post a single balancing transfer that brings customer_AR to the correct `office_penalty` residual:

```php
// Inside cancelBooking, after refundTreasuryAccount and before status update
$expectedCustomerARBalance = $officePenalty;  // the only net amount customer owes
$actualCustomerARBalance = (float) $customerAccount->fresh()->balance;
$correction = $expectedCustomerARBalance - $actualCustomerARBalance;
if (abs($correction) > 0.001) {
    $this->transactionService->recordJournalTransfer([
        'from_account_id' => $customerAccount->id,
        'to_account_id' => $placeholderAccountId, // pending_sales_receivable
        'amount' => abs($correction),
        // direction depends on sign
        ...
    ]);
}
```

### Acceptance criteria for DEFECT-007 fix

1. New regression test for cancel-with-refund (no delete) — assert customer_AR == office_penalty after cancel.
2. Existing 5 baseline scenarios still pass.
3. The DEFECT-005/006 regression tests (CashboxReversalAfterCancelTest) still pass.
4. The H1+H2 walk-back in delete still produces customer_AR == 0 (no double-correction).

## H1 + H2 Order Decision (2026-08-24) — **Option Y**

The team chose **Option Y** (H1 before H2) for the delete walk-back.

**Reasoning**: H1 reverses the cancel's refundTreasuryAccount step; H2 clears the pending_sales_receivable residual from the sale reversal. Running them in **reverse order** of the cancel operations gives the ledger entries a "historical undo" shape that's easier to audit:

```
cancelBooking order:          deleteBookingWithReversal order:
  Step 3 sale reversal         H1: undo refundTreasuryAccount (LAST in cancel)
  FIN-B revenue reversal       H2: clear pending_sales_receivable residual (from Step 3)
  refundTreasuryAccount        
```

Both orders produce the same final state (cashbox = baseline, customer_AR = 0, pending = 0). Option Y is preferred for **auditability**, not correctness.

The fix code (still to be applied in Step 4) follows Option Y.

## DEFECT-008 — cancelBooking loses full sale amount (FlightBookingFlowTest:488)

**Discovered during**: Step 8 verification (2026-08-24) — running baseline comparison after DEFECT-005/006 fix
**Severity**: HIGH — affects every EGP cancel-with-refund currently in production
**Scope**: All cancellations where `total_paid > office_penalty` AND the booking was paid in full upfront (not multi-installment)

### Symptom

When a booking is **fully paid** and then **cancelled with a partial penalty** (i.e., customer gets a refund), the cashbox loses **the entire sale amount** instead of just the refund amount.

Example trace (`FlightBookingFlowTest::test_cancels_booking_with_complete_accounting_rollback` line 488):
- Booking: 18000 EGP selling_price, paid 18000 EGP upfront
- Cancel with penalty: airline=500 + office=200 → total penalty = 700 EGP
- Expected refund: 18000 - 700 = **17300 EGP**
- Treasury after cancel (expected): `treasuryAfterBooking - 17300` (e.g., 68000 - 17300 = 50700)
- Treasury after cancel (actual): `treasuryAfterBooking - 18000` = **50700** → **32700** ❌ (lost the full 18000 instead of just 17300)
- Delta: **18000 EGP lost** (not 17300 — that's the refund loss)

### Why this is different from DEFECT-005/006

| Property | DEFECT-005/006 | DEFECT-008 |
|---|---|---|
| Triggered in | `deleteBookingWithReversal` | `cancelBooking` |
| Lost amount | Refund amount (e.g., 14000) | **Full sale amount** (e.g., 18000, not 17300) |
| Cashbox math | Treasury at 36000 after cancel, should be 50000 after delete | Treasury at 32700 after cancel, should be 50700 (no delete needed) |
| Pattern | Refund walk-back missing in delete | Sale reversal over-reaching in cancel |
| Status | **Fixed by H1+H2** (commit pending) | **Open** — separate backlog |

### Root cause (inside `cancelBooking`)

Three distinct operations are touching the cashbox:
1. **FIN-B revenue reversal** (line ~2437): debits cashbox by `total_paid` (18000), credits customer_AR by 18000
2. **refundTreasuryAccount** (line ~2443): debits cashbox by `refund_amount` (17300), credits customer_AR by 17300
3. **Step 3 sale reversal** (line ~2364): debits pending_sales_receivable by `saleReversalAmount` (18000-700=17300), credits customer_AR by 17300

Net cashbox delta = `-(total_paid + refund_amount)` = `-(18000 + 17300)` = **`-35300`**

But the customer paid only 18000, and refund = 17300, so the cashbox should have lost only **17300** (the legitimate refund). The extra 18000 lost is the sale reversal that didn't have an offsetting income.

In other words: **cancel reverses the full income (18000) PLUS issues the refund (17300)** = 35300 total cash out, but only 17300 was actual cash leaving the business. The 18000 over-debit happens because FIN-B reverses the income entry, but Step 3 sale reversal didn't reverse the same income — they operate on different legs.

### Affected flows

- Any `POST /flight/bookings/{id}/cancel` with `total_paid > office_penalty`
- All EGP bookings where the customer paid in full upfront
- Direct cancellations via `FlightBookingService::cancelBooking()` and any code path that calls it

### What is NOT affected

- Multi-installment bookings (the second/third payment's reversal is handled separately)
- Bookings cancelled with full penalty (refund = 0, FIN-B already balances correctly)
- Direct-delete path (no cancel involved — uses `deleteBookingWithReversal` only)
- DEFECT-005/006 fix in this PR (covers delete path only)

### Proposed fix (out-of-scope for DEFECT-005/006 PR)

The cancel logic needs to **net the income reversal and the refund** into a single transfer that only debits the cashbox by the refund amount. Two possible approaches:

1. **Reverse FIN-B + refundTreasuryAccount as a single net transfer** (preferred):
   ```php
   // Replace FIN-B + refundTreasuryAccount with net transfer:
   // dr cashbox (refund_amount), cr customer_AR (refund_amount - saleReversalAmount)
   ```
2. **Reverse FIN-B only when refund == 0** (full-penalty cancel) and skip the duplicate reversal otherwise

### Acceptance criteria for DEFECT-008 fix

1. New regression test for "book + pay in full + cancel with partial penalty + assert cashbox loss = refund_amount only" (e.g., 18000 paid, 700 penalty, treasury should be down 17300 not 18000).
2. Existing 5 baseline scenarios (1, 4, 5, 6, 7) still pass.
3. The DEFECT-005/006 regression tests (CashboxReversalAfterCancelTest) still pass.
4. Customer AR balance correctly nets to `office_penalty` after cancel (over-correction of DEFECT-007 in the cancel path itself).
5. The FlightBookingFlowTest line 488 assertion (`assertEquals(50700, treasury)`) passes.

### Tracking

## DEFECT-009 — Partial-pay + full-refund cancel + delete loses the refund amount from cashbox

**Discovered during**: Step Coverage-3 (2026-08-25) — running `FlightDeleteCoverageExpansionTest::test_partial_pay_full_refund_cancel_then_delete_returns_all_to_baseline` against clean HEAD with the DEFECT-005/006 fix already applied (commit `3dd46b3`).
**Severity**: HIGH — affects every EGP booking that is partially paid, cancelled with zero penalty, then deleted.
**Test file**: `tests/Feature/Flight/FlightDeleteCoverageExpansionTest.php`
**Test method**: `test_partial_pay_full_refund_cancel_then_delete_returns_all_to_baseline` (lines 243–288)
**Scope**: All `(Pay=P, Cancel=F, EGP, carrier)` bookings. Likely extends to any same-currency `(Cancel=F)` combination.

### Symptom (raw, from `tmp_baseline/coverage_run_unix.txt`)

```
Partial pay + full refund cancel + delete — account 'cashbox' delta != 0 (before=50000, after=42000, delta=-8000)
Failed asserting that -8000.0 matches expected 0.0.

  at tests\Feature\Flight\FlightDeleteCoverageExpansionTest.php:166
```

Fixture / scenario:
- `cashbox` opens at **50000** EGP
- Book 20000 / pay 8000 (carrier source)
- Cancel with **zero penalty** → refund = **8000** (full paid amount returned)
- Delete
- Asserted target: **50000** (back to baseline)
- Actual after delete: **42000**
- **Loss: 8000 EGP** = exactly the refund amount, never walked back

### Why this is **NOT** covered by the DEFECT-005/006 fix

The DEFECT-005/006 fix only handles the case where `total_penalty > 0`. When `total_penalty == 0` (zero-penalty full-refund cancel):

1. The cancel step posts the refund correctly (`refundTreasuryAccount` debits cashbox 8000, credits customer_AR 8000).
2. After cancel: cashbox = 42000, customer_AR = 0, pending_sales_receivable = 0 (clean zero-penalty state).
3. In `deleteBookingWithReversal`, the **`elseif` branch at line 3009** checks `total_penalty > 0.001`. With zero penalty, this branch is **skipped entirely**.
4. The Step 3 sale-reversal branch is also skipped (because `sale_gl_transaction_id` was cleared by the cancel).
5. **No refund walk-back runs.** The 8000 debit from the cancel's `refundTreasuryAccount` is never reversed.

In other words: the H1 fix (added at line ~3139, the new `else` branch that walks back `refundTreasuryAccount`) only fires when there IS a penalty to keep. With zero penalty, the entire cancel-reversal path was already taken by `cancelBooking`, and `deleteBookingWithReversal` does nothing.

### Why this is **NOT** the same as DEFECT-005/006

| Property | DEFECT-005/006 | DEFECT-009 |
|---|---|---|
| Cancel penalty | `> 0` (partial or full) | `= 0` (zero-penalty full-refund) |
| Where loss occurs | `deleteBookingWithReversal` | `cancelBooking` (loss) + `deleteBookingWithReversal` (does not reverse it) |
| Cashbox loss | 12000–14000 (from FIN-A residual sweep) | **Exactly the refund amount** (8000) |
| Fix branch needed | New `else` branch (H1) when `refundCashboxId > 0` AND penalty > 0 | **Same H1 branch extended to penalty == 0**, OR a separate "always-walk-back-refund" branch when the `elseif` is skipped |
| Customer_AR after cancel | +1000 (DEFECT-007 over-state) | 0 (clean zero-penalty state) |

### Root cause

`deleteBookingWithReversal` has a structural gap: when the cancel step already produced a clean ledger (zero penalty → no pending_sales_receivable residual, no customer_AR debt), the `elseif` branch's condition `total_penalty > 0.001` makes the function return without reversing the cancel's own refund leg.

The refund leg in `cancelBooking` is:
