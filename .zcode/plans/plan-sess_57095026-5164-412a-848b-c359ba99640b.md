### B. CLAIMS THAT TURNED OUT TO BE NOT-BUGS (do NOT modify)

- **"Singular vs plural module names cause leakage"** — `transactions.module` uses singular enum values consistently (`'flight'`, `'visa'`, `'hajj_umra'`, `'bus'`, etc.) via `App\Enums\TransactionModule`. `accounts.module_type` intentionally splits between plural (`'flights'`, `'visas'`) for legacy observers and singular elsewhere; `AccountModuleDivision` already bridges the two via `normalizeModuleKey()` / `resolveModuleTypeKey()`. Changing this would be a scope explosion that violates the "minimal change" rule.
- **"OR-chain in `applyCategorySqlFilter` double-counts transactions"** — the cursor iterates each row exactly once regardless of how many SQL branches it matches. The OR-chain is redundant (sub-clause 2 catches every clearing-account row that sub-clause 3 would also catch), but it does not produce duplicate P&L hits.
- **`applySoftDeleteExclusion` cross-contamination risk** — each `whereNotExists` is FQCN-keyed (`t.related_type = App\Models\Bus\BusBooking` etc.) so a chain of 7 AND-joined subqueries cannot match the wrong related row.
- **`matchesFilters()` should include 'general' in tourism** — design intent is that the resolver escalates `'general'` to a real module via the clearing-account lookup before `matchesFilters` runs. This is correct.
- **`getProfitReport` should rename 'expense' → 'expenses' across the system** — `moduleBreakdown()` outputs `'expense'` (singular) and every Vue consumer reads `m.expense` (singular). The plural value already exists nowhere in real data flow; the inconsistency is entirely confined to `getProfitReport()`.

## Implementation Plan

### Phase 1 — Restore Test Infrastructure (REQUIRED FIRST)

**1.1 Fix the migration** — replace 4 raw `DB::statement('UPDATE ... JOIN ... SET ...')` blocks with portable Laravel query-builder loops. Same data result on both engines, zero conditional branches required.

- File: `database/migrations/2026_08_28_000000_convert_online_service_type_and_provider_to_text.php`
- Replace each of 4 statements with:
  ```php
  $codes = DB::table('<master_table>')->whereNotNull('id')->pluck('<code_col>', 'id')->all();
  foreach ($codes as $id => $code) {
      DB::table('online_transactions')
          ->where('<fk_col>', $id)
          ->update(['<code_col>' => $code]);
  }
  ```
- Also replace `listForeignKeys()` (uses `information_schema.KEY_COLUMN_USAGE` which is MySQL-specific) with a portable equivalent: try `Schema::getForeignKeys()` (Laravel abstraction) or guard with `if (DB::getDriverName() === 'mysql')`.
- The `->change()` calls (lines 92-93, 153-155) require `doctrine/dbal` which is already installed.

**1.2 Verify the migration passes** — run `php artisan migrate --env=testing` (or `php artisan test --filter=ProfitLossReportTest`) and confirm the 13 tests now fail at logic-level instead of at migration-level.
