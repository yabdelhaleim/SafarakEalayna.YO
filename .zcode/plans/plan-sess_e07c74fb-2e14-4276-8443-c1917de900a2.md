# Tourism — Full Real-World E2E + Financial Stress Test — Implementation Plan

**Date:** 2026-08-18
**Scope (strict):** Flight + Hajj/Umra + Visa only. Bus is **fully out of scope** — no inspection, no modification, no test coverage.
**Mode:** Report-only (no code fixes applied during the audit).
**Database:** Local MySQL `safarakealayna` (matches `.env`). All created test entities are prefixed `TOURISM_FULL_AUDIT_20260818_*` for safe cleanup. No SQLite migration tests.

---

## 1. Architecture

Single executable PHP orchestrator + phase modules, mirroring the existing audit-script pattern (`audit_visa_module_full.php`, `flight_module_full_e2e.php`, `fawry_module_production_full_test.php`).

```
tourism_full_e2e_audit_20260818.php      # Main orchestrator (runnable)
audit_phases/                             # 20 phase runners
  Phase0_Safety.php
  Phase1_Inventory.php
  Phase2_EmployeeJourney.php
  Phase3_AdminJourney.php
  Phase4_PaymentMatrix.php
  Phase5_Debt.php
  Phase6_InvalidPayment.php
  Phase7_Refund.php
  Phase8_RefundAttack.php
  Phase9_Cancellation.php
  Phase10_SoftDelete.php
  Phase11_PostSaveEditLock.php           # CRITICAL — No-Edit Contract verification
  Phase12_PreCompletionEdit.php
  Phase13_Concurrency.php
  Phase14_CrossModuleAttack.php
  Phase15_Reconciliation.php             # 0.00 EGP tolerance check
  Phase16_Profit.php
  Phase17_TransactionDuplication.php
  Phase18_ReportConsistency.php
  Phase19_FailureInjection.php
  Phase20_FinalVerdict.php
audit_helpers/
  AuditContext.php          # Test entity factory + prefix tagging
  AuditReconciliation.php   # Independent balance/tx SUM helpers + tolerance assertions
  AuditHttp.php             # Laravel HTTP test client for Phase 11/14
  Finding.php               # Finding DTO (severity, module, scenario, expected, actual, diff, tx_ids, root_cause)
  PhaseResult.php           # Aggregator (executed/passed/failed + findings[])
  ReportWriter.php          # Markdown + JSON report writers
tests/reports/
  TOURISM_FULL_E2E_AUDIT_20260818.md     # Human-readable
  TOURISM_FULL_E2E_AUDIT_20260818.json   # Machine-readable
```

**Why this shape:**
- Matches the existing audit-script convention (single runnable file at repo root, require'd phase modules).
- Direct service usage for financial scenarios (faster, more precise) + Laravel HTTP test client only where the spec demands HTTP-layer coverage (Phase 11, 14).
- No `RefreshDatabase` / `DatabaseTransactions` — would destroy the live MySQL DB. Cleanup uses prefix + post-run deletion pass.

## 2. Environment safety gate (PHASE 0)

```php
// 1. APP_ENV must be local

// 2. DB_CONNECTION must be mysql + DB_DATABASE safarakealayna
abort_unless(config('database.default') === 'mysql' && config('database.connections.mysql.database') === 'safarakealayna', 'AUDIT ABORTED: not local MySQL safarakealayna');

config(['audit.prefix' => 'TOURISM_FULL_AUDIT_20260818_']);

// 4. Required services + accounts exist (cashbox, customer accounts)
```

## 3. Per-phase scenarios (3 modules × 2 roles = 6 module-role combinations)

### PHASE 1 — Inventory
- Verify every route in `routes/api.php` (Flight L167-288, Hajj-Umra L572-587, Visa L605-620) exists.
- Verify every controller method exists.
- Verify Vue routes for `/flights/*`, `/hajj-umra/*`, `/visas/*` registered.
- Verify Filament resources exist.
- Verify services `FlightBookingService`, `HajjUmraBookingService`, `VisaBookingService`, `RefundService`, `HajjUmraRefundService`, `VisaRefundService` exist.

### PHASE 2 — Employee journeys (per module)
For each of 100, 500, 999.99, 1000, 2500, 5000, 10000, 25000 EGP:
- Create booking
- Pay (mix of cash + wallet)
- Complete (if applicable)
- Cancel or refund or delete
- Verify accounting

### PHASE 3 — Admin journeys (per module)
Same scenarios as Phase 2 but with `admin` role. Verify Admin does not bypass guards (e.g., admin cannot mutate LOCKED_FIELDS via service stubs).

### PHASE 4 — Payment matrix
- A. 1000 booking / 1000 cash → all accounts match
- B. 1000 booking / 1000 wallet → all accounts match
- C. 1000 booking / 400 wallet + 600 cash → reconcile
- D. 5000 booking / 4 partial payments (1000+750+1250+2000) → reconcile vs single 5000

### PHASE 5 — Debt
5000 booking → pay 2000 (debt 3000) → pay 1000 (debt 2000) → pay 500 (debt 1500) → pay 1500 (debt 0). Verify customer AR ledger, vendor/cost accounts, and cash/wallet accounts at each step.

### PHASE 6 — Invalid payment attacks
Payment > remaining, > debt, negative, zero, empty, invalid decimal, extremely large, duplicate idempotency_key replay, same payment twice, payment after completion/cancellation/refund/deletion, payment against another customer's booking, payment against another module's booking, invalid wallet, invalid account, missing required fields. **Expected:** all reject. No mutation.

### PHASE 7 — Refund happy paths
- Full refund (booking=1000, paid=1000, refund=1000) → all accounts restored
- Partial refund (booking=1000, refund=300, then 700) → final refund = 1000
- Verify RefundAuditLog row created + audit_logs row created

### PHASE 8 — Refund attacks
Refund > paid, > refundable, negative, zero, duplicate, twice, after full refund, after cancel, after delete, another booking ID, another customer ID, manipulated amount, stale data, double-click, retry after timeout. **Expected:** all reject.

### PHASE 9 — Cancellation
Create → Pay → Cancel. Create → Partial Pay → Cancel. Create → Debt → Cancel. Create → Fully Paid → Cancel. Create → Refund → Cancel. Create → Cancel → Refund. Create → Cancel → Delete. Cancel twice. Cancel after refund. Cancel after deletion.

### PHASE 10 — Soft delete / release / reverse
- Delete → financial history preserved
- Delete twice does NOT reverse money twice
- Delete → Pay (reject), Delete → Refund (reject), Delete → Cancel (reject), Delete → Edit (reject)

### PHASE 11 — Post-save Edit lock (CRITICAL — must be ZERO violations)
For each module × each role, attempt every edit path:
- **API:** PUT `/api/v1/flight/bookings/{id}`, PATCH, POST `/bookings/{id}/prices`, equivalent for hajj-umra and visa.
  - Assert HTTP 405/404 (route absent) + 0 financial mutations
- **Direct service:** Call `FlightBookingService::updateBooking()`, `FlightBookingService::updatePrices()`, `HajjUmraBookingService::update()`, `VisaBookingService::update()`, `AviationService::updateBooking()` → expect `LogicException`
- **FormRequest boundary:** Submit `UpdateHajjUmraBookingRequest` with LOCKED_FIELDS → expect 422 from `prepareForValidation()`
- **Filament:** Verify no EditPage registered for FlightBookings/HajjUmraBookings/VisaBookings; Edit actions absent from tables
- **Vue routes:** Verify `/flights/{id}/edit`, `/hajj-umra/{id}/edit`, `/visas/{id}/edit` route is absent (route lookup returns false)
- **Vue stores:** Verify `flightStore.updateBooking`, `hajjUmraStore.updateBooking`, `visaStore.updateBooking` are absent or throw
- **Verify file absence:** `resources/js/views/flights/FlightEdit.vue`, `HajjUmraEdit.vue`, `VisaEdit.vue` deleted (or no Edit button in show page that calls updateBooking with status change — flagged by prior Explore Agent 2)

### PHASE 12 — Pre-completion editing (only where business allows)
Create → Edit amount / customer / payment data / service data. Verify no unintended duplicate tx. (Note: Tourism No-Edit Contract means most editing is forbidden post-create; pre-completion edits to non-financial fields like notes may be allowed — verify what's actually permitted.)

### PHASE 13 — Double submission / concurrency
- Double-click payment → idempotency replay returns same row (200 + `idempotent_replay:true`)
- Two parallel refund requests → second fails (refund.rejected)
- Payment + refund simultaneously → both safe
- Payment + cancel simultaneously → both safe
- Cancel + refund simultaneously → both safe

### PHASE 14 — Cross-module attacks
Use Flight booking ID against Visa refund endpoint → reject. Use Visa ID against Hajj payment endpoint → reject. Use Hajj ID against Flight cancel endpoint → reject. Verify no financial mutation in every case.

### PHASE 15 — Reconciliation (0.00 EGP tolerance)
For every scenario:
```php
$expectedDelta = $booking->total_paid - $booking->total_refunded - $booking->total_cost;
$actualCustomerAccountDelta = $customerAccount->balance - $initialBalance;
$actualCashboxDelta = $cashboxAccount->balance - $initialCashbox;
$actualRevenueAccountDelta = $revenueAccount->balance - $initialRevenue;
$this->assertEqualsWithDelta($expectedDelta, $actualCustomerAccountDelta, 0.00, '...');
$this->assertEqualsWithDelta(-$expectedDelta, $actualCashboxDelta, 0.00, '...');
```
Also `SUM(account_entries.credit) - SUM(account_entries.debit) === account.balance` for every touched account (project invariant).

### PHASE 16 — Profit validation
Per booking: `profit = selling - cost` (where cost = purchase_price + commission etc.). Verify:
- Before payment: profit pending
- After full payment: profit recognized
- After refund: profit reversed
- After cancel: profit reversed
- After delete: profit = 0
- Partial payments: profit NOT recognized twice

### PHASE 17 — Transaction duplication audit
For each scenario, query:
```sql
SELECT COUNT(*) FROM transactions
 WHERE booking_id = ? AND type = ? AND amount = ? -- expect 1
```
For each unique (booking, type, amount) tuple — must be 1. Any > 1 is a finding.

### PHASE 18 — Report consistency
After each scenario, compare booking record vs transactions vs accounts vs cashbox vs wallet vs profit vs debt vs reports endpoint. Zero contradictions.

### PHASE 19 — Failure injection
At difficult points (recordJournalTransfer mid-tx, balance mutation mid-flight, missing account, expired idempotency_key), force exceptions. Verify atomicity (no half-completed state, no orphan transactions, no balance drift).

### PHASE 20 — Final verdict
Compile all findings into:
- `tests/reports/TOURISM_FULL_E2E_AUDIT_20260818.md`
- `tests/reports/TOURISM_FULL_E2E_AUDIT_20260818.json`

```php
class AuditReconciliation {
```

## 6. Cleanup contract

Before run: snapshot baseline (count of customers, accounts, transactions).
After run: `AuditContext::cleanup()` deletes in order:
1. RefundAuditLog rows (where `booking_reference` LIKE `TOURISM_FULL_AUDIT_20260818_%`)
2. AuditLog rows (action LIKE `refund.%` AND user_name LIKE `TOURISM_FULL_AUDIT_%`)
3. Transactions (related_id IN audit booking ids) + AccountEntries
4. Payments (FlightPayment / HajjUmraPayment / VisaPayment where booking_id IN audit ids)
5. RefundRequest rows (flight_booking_id IN audit ids)
6. Bookings (Flight / Hajj / Visa with prefix)
7. Customers (created via AuditContext)
8. Restore any test-modified accounts via `LedgerBalanceMutationGuard::run(fn() => $account->balance = $originalBalance)` if drift detected
