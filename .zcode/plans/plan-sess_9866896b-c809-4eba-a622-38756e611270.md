# Plan: Online Module — Service Type as Text Input + UI Redesign

## Context
- **Production issue**: `/online/execute` dropdowns are all empty because `online_service_types`, `online_service_providers`, `payment_methods`, and `accounts` tables have no rows on the production DB (previous fix added the seed for `payment_methods` only).
- **User's request**:
  1. `نوع الخدمة` (Service Type) → **TEXT INPUT** instead of dropdown (like Fawry's `operation_type`)
  2. Redesign `/online/execute` to match other Create pages (Flight/Bus style)

## Architecture Decision: Follow the Fawry Pattern

Fawry already has the exact pattern the user wants:
- **Storage**: `operation_type` is a `string(50)` column (not a FK)
- **Vue**: `<input v-model="form.operation_type" type="text" placeholder="اكتب نوع العملية" />`
- **Validation**: `'required', 'string', 'max:50'`
- **Display lookup (optional)**: `belongsTo(FawryOperationType::class, 'operation_type', 'code')` joins against `fawry_operation_types.code` for showing the Arabic name in lists/reports — but the **input is free text**

We'll apply the **same pattern** to Online's `service_type`.

## A. Backend Changes

### A.1 — New Migration: `service_type_id` (FK) → `service_type_code` (text)

**New file:** `database/migrations/2026_08_28_000000_convert_online_service_type_to_text.php`

Steps:
1. ADD `service_type_code` (string, 80, nullable) column on `online_transactions`
2. Backfill: `UPDATE online_transactions t JOIN online_service_types s ON t.service_type_id = s.id SET t.service_type_code = s.code`
3. Drop the FK constraint (`$table->dropForeign(['service_type_id'])`)
4. Drop the `service_type_id` column
5. Convert `service_type_code` to NOT NULL **only if** all rows were backfilled (`SELECT COUNT(*) WHERE service_type_code IS NULL` = 0). Otherwise keep nullable with a check.

Safety: if existing rows can't be backfilled, we surface a clear migration error rather than silently dropping data.

### A.2 — Model: `app/Models/Online/OnlineTransaction.php`

- Replace `'service_type_id'` with `'service_type_code'` in `$fillable`
- Replace `serviceType(): BelongsTo` relation with `serviceTypeRow(): BelongsTo` (mirrors Fawry's `operationTypeRow()`):
  ```php
  public function serviceTypeRow(): BelongsTo
  {
      return $this->belongsTo(OnlineServiceType::class, 'service_type_code', 'code');
  }
  ```
- Update `scopeByServiceType()` to filter by `service_type_code` (string)

### A.3 — Request: `app/Http/Requests/Online/StoreOnlineTransactionRequest.php`

- Replace:
  ```php
  'service_type_id' => [
      'required', 'integer',
      Rule::exists((new OnlineServiceType)->getTable(), 'id')
          ->where(fn ($q) => $q->where('is_active', true)->whereNull('deleted_at')),
  ],
  ```
  with:
  ```php
  'service_type_code' => ['required', 'string', 'max:80'],
  ```
- Update `prepareForValidation()` if it touches `service_type_id`
- Update `withValidator()` Arabic messages to reference `service_type_code`
- Same change in `UpdateOnlineTransactionRequest.php`

### A.4 — Controller / Service

- `app/Http/Controllers/Api/V1/Online/OnlineTransactionController.php`: search-and-replace `service_type_id` → `service_type_code`
- `app/Services/Online/OnlineTransactionService.php`: same

### A.5 — Filament: `app/Filament/Admin/Resources/OnlineTransactions/OnlineTransactionResource.php`

- Replace `Select::make('service_type_id')->relationship(...)` with `TextInput::make('service_type_code')->label('نوع الخدمة')->required()->maxLength(80)`
- Update table `TextColumn::make('service_type_code')` (showing the raw code, with optional `formatStateUsing()` to look up the Arabic name via `OnlineServiceType::where('code', $state)->value('name_ar')` if a master row exists)

### A.6 — Keep `online_service_types` table + Filament resource

The `online_service_types` table stays. It now becomes an **optional lookup**:
- Admin can still add/manage types via `OnlineServiceTypeResource` in Filament
- The text input doesn't reference it directly (free-form)
- Display joins via `serviceTypeRow()` for showing Arabic labels in lists/reports

This is the **Fawry pattern**: master data exists for management, but the input is free text.

### A.7 — Frontend Lists

- `resources/js/views/online/OnlineIndex.vue`: if `service_type_id` is referenced for filtering/display, switch to `service_type_code` (raw text). Optionally resolve via `OnlineServiceType` lookup for Arabic label.
- `resources/js/views/online/OnlineTreasury.vue`: same audit.
- `resources/js/views/online/OnlineCustomerBalances.vue` and any others: same audit.

## C. Provider (المزود) Decision

The user only specified **نوع الخدمة** as text. **المزود** has two reasonable choices:
- Keep as dropdown (requires `online_service_providers` to be seeded — 6-7 minutes via the existing seeder)
- Convert to text input too (matches Fawry's `fawry_machine_id` which IS a dropdown, so no precedent here)

**Recommendation:** Keep Provider as dropdown. Seeding is a 5-minute operation:
```bash
php artisan db:seed --class=OnlineModuleProductionTestSeeder
```
This populates 5 providers, 6 service types (still useful for the Admin to manage), 6 payment methods (now redundant), and cashbox accounts.

If user wants Provider as text too, add to plan as a separate change.

## E. Testing Plan (manual)

1. **Migration dry-run locally** before deploying — confirm backfill works on a fresh DB and on a DB with existing transactions
2. **Submit a transaction** with text `service_type_code` and verify it persists correctly
3. **Edit an existing transaction** in Filament and confirm `TextInput` shows the saved code
4. **Display** the transaction in OnlineIndex and verify the Arabic label appears if a matching `OnlineServiceType` row exists
5. **Verify stepper navigation**: can move forward only when current step is valid; can submit from Step 3
6. **Verify all dropdowns that depend on seeded data**:
   - Customer (drop-down, depends on `online` module_type customers)
   - Provider (drop-down, depends on seeded `online_service_providers`)
   - Payment Method (drop-down, depends on `payment_methods` — already seeded by prior fix)
   - Account (drop-down, depends on seeded `accounts`)

## F. Rollback Plan

If issues arise:
1. **Schema rollback**: The migration includes `down()` that re-adds `service_type_id` as nullable, drops `service_type_code` after backfilling from `online_service_types.code` JOIN.
2. **Feature flag fallback**: We can keep the old Vue page in `git history` and revert via a single commit.
3. **Data preservation**: We backfill `service_type_code` from `service_type_id` BEFORE dropping the column, so existing transactions are never lost.
