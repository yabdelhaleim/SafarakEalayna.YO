## Hajj/Umrah Module — Complete Testing Plan

### Context

The Hajj/Umrah module already has **33 test files (~500 tests)** covering booking lifecycle, cancellation, refund, delete-with-reversal, payments, idempotency, multi-currency, FX, authorization, dashboard, treasury, executing companies, and supplier flows. Existing tests already prove zero-ghost balance after delete, additive reversals, and double-entry integrity per booking.

The user wants a **complete audit broken into parts**, with a specific emphasis on:
- Confirming **all existing tests pass** against current code (baseline)
- Proving **deletion/cancel/refund restores every account, customer debt, and supplier/receivable to its pre-booking baseline** (the consolidated scenario the user described)
- Filling **identified gaps** in coverage

### Plan — 4 Parts

### PART 2 — New Comprehensive Baseline-Restore Audit

**File**: `tests/Feature/HajjUmra/HajjUmraFullBaselineRestoreTest.php`

A single, definitive test class that proves the user's exact requirement: every account balance, customer debt, supplier AP, executing-company AP, and customer-receivable returns to pre-booking baseline after a full lifecycle (create → multiple payments → cancel/refund/delete).

**Setup**: Captures a `baselineSnapshot()` of every Account.balance + Customer.total_debt + supplier/receivable aggregate. Performs booking operations. Captures `finalSnapshot()`. Asserts `final == baseline` (within 0.01 rounding).

**Tests**:

1. `test_create_then_delete_restores_every_balance_to_baseline` — Treasury-as-source booking (no supplier, no executing company), single currency EGP, full payment, then admin DELETE.
2. `test_create_with_supplier_then_delete_restores_every_balance_to_baseline` — Supplier-USD booking with EGP clearing, full payment, then DELETE.
3. `test_create_with_executing_company_then_delete_restores_every_balance_to_baseline` — Executing-company-SAR booking with EGP clearing, full payment, then DELETE.
4. `test_create_then_cancel_restores_every_balance_to_baseline` — Same as #1 but light cancel (status flip + additive reversal, no soft-delete).
5. `test_create_then_refund_restores_every_balance_to_baseline` — Same as #1 but full refund.
6. `test_partial_paid_then_delete_restores_every_balance_to_baseline` — Pay 60% of selling price, then DELETE.
7. `test_multi_payment_then_delete_restores_every_balance_to_baseline` — 3 payments split across cash/bank/wallet, then DELETE.
8. `test_baseline_restored_when_customer_pays_via_general_receipt_then_booking_deleted` — Cross-endpoint: customer pays via general receipt (not via `addPayment`), then booking is DELETEd. Verifies that the general-receipt credit to customer AR is also reversed.
9. `test_baseline_restored_for_two_customers_independently` — Two customers with bookings; deleting one must not affect the other.
10. `test_baseline_restored_with_cross_currency_paid_in_booking_currency` — Customer pays USD via payment against an EGP booking's debt (cross-currency customer AR / customer payment account). Must still zero out.
11. `test_customer_balances_endpoint_shows_zero_debt_after_full_lifecycle_delete` — Verifies the `GET /hajj-umra/customer-balances` API correctly shows `total_debt == 0` after the booking's full reversal.
12. `test_customer_statement_running_balance_returns_to_zero_after_delete` — Verifies `GET /hajj-umra/customer-statement` shows final `running_balance == 0` after reversal.

**Helper methods**:
- `snapshotBalances()` → returns `['accounts' => [...], 'customer_debts' => [...], 'company_aps' => [...]]`
- `assertBaselineRestored($baseline, $label)` → compares snapshots; asserts no delta > 0.01

### PART 3 — Gap-Coverage Tests (3 new files)

#### 3a. `tests/Feature/HajjUmra/HajjUmraHotelAndTripSupervisorCrudTest.php`

Hotel & TripSupervisor are referenced via settings endpoints only — CRUD is not directly tested.

**Tests** (6):
1. `test_create_hotel_via_observer_or_factory_then_retrieve` — Hotel model + factory (if exists) or via Program relation.
2. `test_trip_supervisor_appears_in_settings_endpoint` — Reference list endpoint.
3. `test_create_booking_with_trip_supervisor_via_program_persists_relation` — Verify program → tripSupervisor linkage is persisted.
4. `test_program_with_hotel_and_supervisor_shows_in_booking_resource` — Booking resource includes nested hotel/supervisor.
5. `test_accommodation_type_settings_endpoint_returns_correct_enum` — Verify enum coverage.
6. `test_hotel_does_not_break_booking_when_null` — Defensive: bookings without hotel still succeed.

#### 3b. `tests/Feature/HajjUmra/HajjUmraMultiCurrencyPartialCancelTest.php`

Partial-payment-then-cancel on multi-currency booking is not explicitly tested together.

**Tests** (4):
1. `test_partial_paid_usd_booking_then_cancel_returns_supplier_ap_to_zero` — USD supplier + EGP clearing, pay 40%, then cancel.
2. `test_partial_paid_egp_booking_then_refund_caps_at_paid_amount` — EGP booking, pay 30% of selling, then refund; verify refund amount = paid (not selling).
3. `test_partial_paid_then_delete_zeroes_every_account` — EGP booking, pay 50%, DELETE; verify all accounts zero.
4. `test_overpayment_then_cancel_still_zeroes_baseline` — Customer overpaid (paid > selling); cancel reverses only the original income + actual payments, not phantom amounts.

#### 3c. `tests/Feature/HajjUmra/HajjUmraPayDebtCrossEndpointTest.php`

Cross-endpoint pay-debt (general receipt on customer AR not tied to any booking) reflected in customer_balances / statement.

**Tests** (4):
1. `test_general_receipt_against_customer_ar_appears_in_customer_balances` — POST a general journal receipt to a customer's AR account, verify `GET /customer-balances` `total_paid` includes it.
2. `test_general_receipt_appears_in_customer_statement_as_payment_line` — Verify `GET /customer-statement` shows it as `سند قبض`.
3. `test_general_receipt_then_addPayment_on_booking_does_not_double_count` — Customer pays 1000 via general receipt + 500 via booking payment; verify totals = 1500 (not 2000).
4. `test_general_receipt_then_booking_delete_only_reverses_booking_leg_not_general` — DELETE booking; general-receipt credit remains, booking-related entries reversed; net balance per statement.
