## 1. F-1 (P0) — Duplicate `booking_reference`

**Files:** `app/Services/Flight/FlightBookingService.php:294` (forces `FLT-{n}`, ignores user input); `flight_bookings` migration (no UNIQUE); `StoreFlightBookingRequest.php` (no uniqueness rule).

**Root cause:** `createBooking()` silently overwrites user-supplied `booking_reference`. Two identical POSTs return 201 twice; DB grows. No idempotency.

**Fix (3 layers):**
1. New migration `2026_xx_xx_add_unique_index_on_flight_bookings_reference.php` — UNIQUE INDEX (backfill dups first).
2. `createBooking()`: if `data['booking_reference']` provided and exists in DB → throw `DuplicateBookingReferenceException`.
3. `StoreFlightBookingRequest::rules()` — add `'booking_reference' => [..., Rule::unique('flight_bookings','booking_reference')]`.

**Impacts:** DB new UNIQUE INDEX; API 422/409; Filament form validation; Vue inline error. **Regression risk: HIGH** if production has dupes.

**Tests:** NEW T-DUP-1..4 (duplicate POST → 422; delete+recreate → 201; auto-gen unique; concurrent POSTs). UPDATE V-20 in fvm_combined (currently passes via silent override → must assert 422).

## 2. F-2 (P0) — No admin middleware on Flight routes

**Files:** `routes/api.php:167-263` — 99+ routes, only `auth:sanctum + active`. Compare Bus (`role:admin` for DELETE) and Finance (`admin` for writes).

**Root cause:** Outer middleware provides auth but no role check. Any active user can refund/recharge/cancel.

**Fix:** Split Flight routes:
```php
Route::prefix('flight')->group(function () {
    Route::get('bookings', ...); Route::get('bookings/{id}', ...); // GETs — all authed
    Route::middleware('admin')->group(function () {
        Route::post('bookings', ...); Route::put('bookings/{id}', ...);
        Route::delete('bookings/{id}', ...); Route::post('bookings/{id}/cancel', ...);
        Route::post('bookings/{id}/payments', ...); Route::post('carriers/{id}/recharge', ...);
        Route::post('treasury/systems/{id}/recharge', ...);
        // ... all money-moving POSTs
    });
});
```

**Impacts:** API 403 for non-admin writes; Vue hides destructive buttons. **Regression risk: MEDIUM.**

**Tests:** NEW T-MW-1..5 (admin POST=201, employee POST=403, employee GET=200, employee cancel=403, admin recharge=200). UPDATE V-21 (currently asserts employee CAN create → must assert 403) and A3.

## 3. F-3 (P0) — Negative account balances possible

**Files:** `Account.php` (balance is `decimal:2` no CHECK); `AccountService.php`; `LedgerBalanceMutationGuard.php`; `accounts` migration; `FlightBookingService.php:1888` (uses `>` not `>=`).

**Root cause:** No DB CHECK on `balance >= 0` for liquidity accounts. Service guards exist but buggy service paths can produce negatives.

**Fix (3 layers):**
1. Migration `2026_xx_xx_add_non_negative_balance_constraint_on_accounts.php`:
   ```sql
   ALTER TABLE accounts ADD CONSTRAINT chk_balance_non_negative CHECK (
       (type IN ('cashbox','bank','wallet') AND balance >= 0)
       OR (type NOT IN ('cashbox','bank','wallet'))
   );
   ```
2. `AccountService::debitAccount()` throws `InsufficientFundsException` if `balance < amount`.
3. `LedgerBalanceMutationGuard::run()` rejects negative final balance for liquidity.

**Impacts:** DB new CHECK (may fail on existing negatives — reconcile first via `LedgerRepairService`); new exception → 422; UI "Insufficient funds" error. **Regression risk: HIGH** if production has negatives.

**Tests:** NEW T-NEG-1..4 (debit cashbox below 0 → exception; direct update rejected; payment causing negative cashbox → reject; DB query: 0 negative liquidity). UPDATE N5.

## 4. F-4 (P1) — Cashbox balance drift vs entries

**Files:** `LedgerReconciliationService.php` (detects drift); `LedgerRepairService.php` (`rebuildBrokenBalanceAfterChains`, `syncCustomerBalancesFromLedger`); `LedgerReconcileCommand.php` (daily 03:10); `scripts/flight_audit_setup.php` (seeds `balance` directly, no opening entry).

**Root cause:** Audit seed creates accounts with starting `balance` but no opening `account_entries`. `balance != SUM(entries)` is GUARANTEED. Daily self-heal would fix in production if data were correct.

**Fix:**
1. Update `scripts/flight_audit_setup.php` — create opening `account_entries` row for each seeded cashbox/treasury.
2. Production: `php artisan ledger:reconcile --json`; capture `accounts_with_balance_drift`.
3. New `AccountInvariant` runs after `AccountEntry::saved()`; auto-rebuild if drift > 0.02.

**Impacts:** New opening entries on reseed. **Regression risk: LOW** — self-heal already exists.

**Tests:** NEW T-RECON-1..4 (reconcile drift == 0; after phase_all still 0; seed has opening entries; mutation+payment correct). UPDATE J1.

## 5. F-5 (P1) — Multi-currency payment leaves 1500 EGP residue

**Files:** `FlightBookingService.php:1772-1964` (`addPayment()` with 4 currency branches); `:691-735` (`egpPerUnitOfCurrency` using `FALLBACK_EGP_PER_UNIT`); `FlightBooking.php` (`exchange_rate`, `selling_price_egp`).

**Root cause (preliminary):** `createBooking` and `addPayment` may use DIFFERENT exchange rate snapshots. For USD booking + USD pay: rate R1 vs R2 (e.g., 50 vs 48.5) → 1000 × (50−48.5) = 1500 EGP residue. **Matches T3 exactly.**

**Fix (investigation first):**
1. Add detailed logging to both methods capturing exact `exchange_rate` used.
2. Re-run T3 with verbose logging to confirm root cause.
3. In `addPayment`: enforce `$rate = (float) $booking->exchange_rate` for ALL conversions.
4. Add post-conversion assertion:
   ```php
   if (abs(($totalPaid + $transferAmount) - $booking->selling_price_egp) > 0.02 && $booking->paid_amount >= $booking->selling_price_egp) {
       throw new \Exception('Currency mismatch on settlement');
   }
   ```

**Impacts:** DB no change. **Regression risk: MEDIUM.**

**Tests:** NEW T-CURR-1..5 (USD+USD balance 0; USD+EGP balance EGP delta; EGP+USD converted; SAR+SAR 0; mixed stress). UPDATE T3 + H tests.

**Impacts:** DB no change. **Regression risk: LOW.**
